# Vision: Phraise

Status: active
Author: Seb Kurella (owner), transcribed and lightly structured by lead agent (Fable 5.1)
Updated: 2026-09-27

## The problem

Google Docs is disliked for structural reasons: too many formatting options, version control is not a first-class construct, it cannot live on the same medium as code, and the comment authoring experience is poor. Yet it works, because:

- the collaborative editing experience is great,
- there is an offline mode,
- you can post comments,
- it supports widgets such as people selectors and status selectors.

Markdown is the preferred authoring format for meeting minutes, design docs and similar: opinionated and minimal. Git is a great storage format at "watermarks", the moments a user chooses to save. Typora is a great renderer. But format plus watermark storage plus a local editor are not enough to replace Google Docs. Missing: a storage backend and an editing frontend that support collaborative editing and comments. Extensibility is a cherry on top, out of scope for now.

## The product

Elevate Markdown, Git and GitHub to a Google Docs authoring experience.

Original ideas, treated as inspiration rather than spec:

- Log in with GitHub, open an arbitrary file from an arbitrary repository the user has access to, on any branch or tag.
- Edits on a branch are not committed until explicitly requested. In-progress edits are "staged" somewhere: either a dedicated extra branch on GitHub, which may strain GitHub at scale, or a separate state service we own.
- Multiple users on the same branch see everyone's in-progress edits, attributable to individual users.
- Comments are stored either in a GitHub PR, if PRs support comments on arbitrary lines of arbitrary files, or in a state service we own. Dedicated branches could serve comments on uncommitted content.

The feel we are going for:

- **Opinionated toward rich text.** Pasting and copying Markdown is supported, but the primary experience is Google-Docs-like. A non-technical user should not need to know it is Markdown or Git underneath.
- **AI has first-class access.** Agents read and edit these files as easily as local Markdown files, through a skill or MCP that exposes comments, uncommitted content and so on.
- **Smooth transition** between the online platform and raw files in the repo.
- **IDE integration**, for example a VS Code plugin where the user runs their agent while seeing collaborative progress.
- Optionally, inline AI chat using the user's own AI account. (Research shows this is not permitted for Claude subscriptions; see the architecture decisions doc.)
- Later: graphical authoring of Mermaid, comments on Mermaid boxes and arrows, then other plugins.

## Constraints and worries

- State outside Git/GitHub makes enterprise adoption harder. The project should be FOSS first, possibly a startup later. Tradeoffs may hurt usability, and GitHub may object to being used as a database.
- Data-model paper cuts: what if a file is not valid Markdown? How are conflicts handled? Heuristics or AI are not always sufficient. A user merging branches may accept a confirmation dialog, but an external commit or a user leaving offline mode should not require one.

## Priorities for how the work is run

- Derisk key architecture decisions first so there are no major rewrites or impossible problems later.
- The owner talks to a single lead agent (Fable). Other agents should be cheaper models.
- Parallelism is not a goal. Autonomy, good context management and quality at reasonable cost are.
