## Task 2 (continued) — a side effect noticed during vacuity work

After the `npm run gates` run in task 1 and the three vacuity re-builds, `git status` in the clone showed 4 of the 10 committed `screenshots/*.png` modified (same byte size ±3 bytes, different MD5). Cause: `e2e/gateJ-feel.spec.ts`'s `screenshotAndCheck()` writes `page.screenshot({ path: ... })` directly into the tracked `screenshots/` directory and asserts only `size < 300 KB` — it does not assert on screenshot content. Every `npm run gates` (or any run of gateJ-feel.spec.ts) run therefore overwrites the committed screenshots with a fresh, slightly different (font/AA/timing) capture and leaves the working tree dirty; nothing catches a visual regression except a human looking at the diffed PNGs, which is disclosed and was in fact done by the orchestrator (23:50 log entry) but is not part of the gate command's own pass/fail. Not a blocker (charter only requires the screenshots exist, under 300 KB, for the owner to judge by eye) but worth the lead's attention: running `npm run gates` on a real checkout (not a throwaway clone) always dirties tracked binaries.

**Follow-up: gate E reproduces, not a rare flake.** Ran `npx playwright test e2e/gateE-undo.spec.ts --project=chromium --repeat-each=5` (15 runs of 3 tests): the same test ("Alice and Bob type alternately...") failed **5 of 5** times, always at the same assertion (`gateE-undo.spec.ts:88`, inside `placeCaretAtEnd`, second call at line 187), always `expected 36, received 33`. 33 = length of `ALICE_TEXT + ' A1'` (missing Bob's `' B1'`, 3 chars). Reading the test (`e2e/gateE-undo.spec.ts`): the preceding line polls `selectionInfo(page).text` to equal the 36-char string and that check passes (failure is on the *next* line, the offset check after pressing `LINE_END`), meaning the paragraph briefly shows the full converged text, then `LINE_END`'s reported offset lands 3 short — consistent with a transient/regressing collab state right as the local caret is repositioned, i.e. the same class of caret/position bug the orchestrator's log (19:34 entry) attributes to `@tiptap/y-tiptap`'s `restoreRelativeSelection`/`recoverSelectionEndpoint`, for which brief 05 added the `localCaretFollow` workaround plugin. This specific interaction (idle-then-repositioned local caret right after a remote insert, inside the SAME undo test the workaround was built for) was not covered by that workaround, or regressed since. On this machine it is 100% reproducible in isolation, not the "roughly 1 in 100-150" or "one retry in 360" rate the orchestrator's log describes for other symptoms in this area — this looks like a distinct, more severe manifestation. This is a genuine product-relevant instability in gate E's own subject matter (caret correctness under concurrent typing), not a harness artifact: the assertion is on the real ProseMirror selection state after real keyboard input.
