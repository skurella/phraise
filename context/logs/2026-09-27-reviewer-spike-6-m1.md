**Gate B: the check is real for the attack it tests, but the attack it tests is not the only way to forge an update, and the relay's actual defense has a live bypass — not just the residual the code comments describe.**

`src/relay/forgery.ts`'s `checkForgery` only inspects messages of y-protocols type `SYNC_UPDATE` (2); it returns immediately for type `SYNC_STEP2` (1) ("residual" per its own comment, framed as limited to legitimate reconnect-after-relay-restart). But `node_modules/@hocuspocus/server/src/MessageReceiver.ts` and `node_modules/y-protocols/sync.js` show `messageYjsSyncStep2` and `messageYjsUpdate` both resolve to the literal same function (`export const readUpdate = readSyncStep2`) — `Y.applyUpdate` under a connection-origin transaction, broadcast the same way. Nothing restricts a SyncStep2-tagged message to a connection's first message; the server accepts one at any time from any already-authenticated connection.

**Reproduced live**, in the temp clone only (`scratch-syncstep2-forgery2.mts`, deleted after use, never in the worktree): started a relay, connected alice and mallory, had alice make a real edit. Cloned the relay's current full state into a scratch `Y.Doc` (never touching its own clientID, so Yjs's own same-ID collision defense never triggers), then reassigned that scratch doc's `clientID` to alice's real clientID and made a local edit — Yjs assigns the new item's clock as a genuine continuation of alice's existing sequence (not a colliding/duplicate range, which is what a naive "brand-new Y.Doc under the victim's id" forgery — the technique gate B itself and my first reproduction attempt used — produces, and which Yjs silently no-ops regardless of `checkForgery`). Sent the resulting update as a raw wire message tagged `MessageType.Sync` + `messageYjsSyncStep2` (built with `lib0/encoding` + `y-protocols/sync.writeSyncStep2`, mirroring `@hocuspocus/provider`'s own `SyncStepTwoMessage.get()`) over mallory's already-authenticated websocket.

Result: `forgedRejections` counter stayed at 0 (never incremented); the relay's canonical document **did contain the forged text** (`RELAY document now contains the forged text? true`); the victim's own live editor **received and displayed the forged text** (`ALICE ... now sees the forged text in her own editor? true`); mallory's connection was **not** closed (`open connections after send: 2`, unchanged). Every one of gate B's own pass criteria ("never contains the forged text", "forger's connection is closed", "rejection counter is 1") is violated by this variant, using only an authenticated connection any of gate B's own users already has.

**Verdict: BLOCKER.** Charter gate B: "A forged client identity is rejected by the relay before the update is applied" is not met in general — only for updates tagged as message type 2. Gate B as written does not test this and so currently reports PASS while the property it names is false. This is exactly the "gates that pass without testing what the charter asks" case brief 05 asks to find, plus a real security bug (not just a weak test) that milestone 2 onward (rebase, daemon, system fuzz) would inherit silently.
Suggested fix (one sentence): move the clientID check to run for every y-protocols message type that can carry structs (`SYNC_STEP2` and `SYNC_UPDATE` both), and if `SYNC_STEP2` must stay permissive for a *bona fide* first-sync-after-restart case, gate that permissiveness on "this is the connection's first sync message" (a per-connection flag), not on the message's declared type alone.
File: `src/relay/forgery.ts:73-88` (the `type !== SYNC_UPDATE` early return), `src/relay/server.ts:117-130` (`beforeSync` wiring).

## 18:50 — task 4: look-ahead risks for milestones 2-4

1. **(Minor/moderate, perf) Repeated whole-document block walks.** `src/crdt/blocks.ts`'s `collectBlocks` walks every textblock ever created (live or deleted, since `gc:false`) from the fragment root; `blockStatesAt` calls it once per invocation, but `engine/integrate.ts`'s `processRecord` calls `blockStatesAt` **three times** (statesA/statesB/statesP) per pending rebase record, and `blockHasOwnEditsSince`/`resurrectBlock` each do their own separate `collectBlocks(doc).find(blockId)` on top of that — so a replica that has been offline through several external commits (milestone 2's gate F/G, and milestone 4's system fuzz with relay restarts and offline periods) pays `O(pending records × blocks-ever-created)` on the batch that reconnects it, with several redundant full-document walks per record. D1's re-seed-after-commit bounds this between commits, but a long offline period with several external commits before reconnecting, or milestone 4's 240KB document (gate M) with many blocks, could make this the dominant cost. Worth measuring explicitly in gate M rather than assuming D1's bound is small enough in practice.
2. **(Note, not yet a defect) Restore does not yet rebase.** `seeding.ts`'s restore path only accepts a draft whose `base === head`; a restore where the branch head moved past the draft's base while the relay was down falls through to a fresh seed **from head**, silently discarding the draft's uncommitted content instead of rebasing it forward. Brief 04 places "the rebase case" explicitly out of scope for milestone 1 and into brief 06 (milestone 2), so this is not a milestone-1 defect, but it is worth confirming brief 06 actually closes this exact path (restore-then-rebase), not just "poll implies open document, live-edit rebase" — a restore that happens to race an external commit is a distinct code path from the live-poll rebase and I did not see it named explicitly in plan section 6's "Restore" bullet beyond "the rebase case comes in brief 06."
3. **(Carries forward) The gate-B forgery gap (blocker above) will propagate.** Milestone 2's rebase/head-poller and milestone 3's daemon both add more replicas and more message traffic through the same relay/forgery path; milestone 4's system fuzz (300 trials, hostile-adjacent scenarios) will not surface this gap on its own unless a trial specifically crafts a mis-tagged message, since ordinary `HocuspocusProvider` clients never do this deliberately. Recommend fixing this before, not after, milestone 2, since every later milestone's fuzz/scale gates implicitly assume gate B's guarantee holds.
4. **(Watch, not yet exercised) Integration hook untested end-to-end.** `attachIntegration`/`processRecord`/resurrection have engine-level unit tests (brief 03) but no milestone-1 gate exercises them against a live relay + live editors, since no rebase happens yet in milestone 1. Milestone 2's gate F is the first real integration test of this path on the full schema (tables, images, footnotes) rather than spike 2's single-`XmlText` schema; recommend the milestone-2 reviewer treat gate F's "blocks changed on both sides are flagged" check as high-priority, since the generalization from spike 2's schema is exactly the kind of change that survives unit tests but breaks on integration.
