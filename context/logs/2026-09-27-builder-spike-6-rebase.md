### Design for task 1 (forgery, all message types)

Reviewer's blocker: `checkForgery` only ran for `SYNC_UPDATE` (type 2); a raw `SYNC_STEP2` (type 1) carrying a forged clock range under another user's clientID bypassed the check entirely. Fix: run the same clock-range check for both SYNC_STEP2 and SYNC_UPDATE (SYNC_STEP1 carries only a state vector, never structs, so it stays exempt). Two escapes replace the old blanket message-type exemption:
1. "the relay already holds every clock in that range" -- checked via `Y.getState(doc.store, clientId) >= range.to` (new `crdt.knownClock`); this is what makes an honest reconnect-after-restart's syncStep2 (which resends the client's own already-known history, including other users' structs the relay already has) a harmless no-op, without opening a hole for genuinely new forged structs.
2. "the document is in a recovery window" -- a 60s (default) window opened when a document is freshly seeded or restored from a draft after having no local base (i.e. local state was actually lost or this is the first-ever open), tracked relay-side in `RelayState` (not in the CRDT doc itself -- it is relay policy, not document content). During the window, ranges that fail check 1 are accepted anyway and counted separately (`relayedDuringRecovery`), never rejected, and never re-attributed (recordAttribution's existing "leave mapped ids alone" behavior already does this). This is a documented residual: a forgery timed to land inside another document's recovery window is not caught. Logging this now; will restate in relay/README.md.

Next: implement in src/crdt/inspectUpdate.ts (knownClock), src/relay/forgery.ts, src/relay/state.ts, src/relay/seeding.ts (also folds in task 4's restore-then-rebase), src/relay/server.ts.

**Real bug found and fixed** (not introduced by this brief, but the first scenario to exercise it): `engine/commit.ts`'s `recordCommit` stored `prepareCommit`'s snapshot -- taken BEFORE `recordCommit`'s own `base`/`lastCommit`/`editorsSinceCommit` writes -- under the NEW commit's `snapshot:<commit>` key. A later rebase forks from that snapshot (`Y.createDocFromSnapshot`) and its `onFork` overwrites `base` under the rebase's own deterministic peer id, marking (from the fork's stale point of view) the PRE-commit `base` entry as superseded. But `doc` had already moved past it via `recordCommit`'s own (chronologically later, same live clientID) write, which the fork's history never saw. Merging the fork's update back left two causally-unrelated items for the same `phraise.base` Y.Map key; Yjs's own tie-break (comparing item/client ids) decided the winner non-deterministically from this code's point of view -- silently reverting the rebase's base pointer roughly half the time. Reproduced directly (isolated repro script, since deleted) with gate E's own "commit, then an external commit lands, then commit again" sequence: 3/5 raw runs failed with a spurious `409 stale` even though the expected head genuinely matched the remote. Root cause confirmed by instrumenting `recordCommit`/`rebase()`: the rebase's own `applied:true` result was real, but a `getBase(doc)` read immediately after showed the value had already reverted to the pre-rebase commit. Fixed by reordering `recordCommit` to take its stored snapshot AFTER its own meta writes (matching `seed.ts`'s `seedFromCommit`, which already does this correctly) -- confirmed by 5/5 clean gate E runs afterward. `engine.commit.test.ts`'s existing assertions still pass (it never exercised this path: single sequential same-clientID writes never trigger the Y.Map conflict). Logging here since it changes behavior of code from an earlier brief; will note in relay/README.md's decisions if the orchestrator wants it promoted to the findings doc.
